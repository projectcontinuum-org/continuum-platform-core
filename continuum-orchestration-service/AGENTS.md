## Purpose

Temporal workflow implementation. Executes workflow DAGs — resolves task queues, dispatches node activities in parallel, tracks completion/failure, streams status events to Kafka. This is a standalone Spring Boot service, not a library.

## Ownership

Core platform team. Container image: `projectcontinuum/continuum-orchestration-service`.

## Local Contracts

- `ContinuumWorkflow` (`@WorkflowImpl` on `WORKFLOW_TASK_QUEUE`) — main orchestration loop. Does not execute node logic; only dispatches activities and aggregates results.
- `InitializeActivity` (`@ActivityImpl` on `ACTIVITY_TASK_QUEUE_INITIALIZE`) — resolves node → task queue mapping by calling `POST /api/v1/node-explorer/nodes/task-queues` on the API server. Retries until all node queues are resolved (workers may start after the workflow).
- DAG execution: `NodeReadiness` (pure, no mutation) decides per loop iteration. `getReadyNodes()` returns untouched nodes whose every incoming edge delivered its source port. `getNodesToSkip()` returns untouched nodes that can never run: an unconnected declared input, or a broken incoming edge (source `FAILED`/`SKIPPED`, or finished without producing the port), applied transitively. `toleratesBrokenEdge()` is the extension point for branch conditions. `Async.function {}` starts ready nodes concurrently. `Promise.anyOf()` races all pending promises — the loop continues until no nodes remain.
- Flow variables:
  - `WorkflowDagExecutor.getNodeInputs` adds `inputs["$variable"]` only when it is non-empty. The value comes from `FlowVariableMerger.collectInputVariables`, which is pure and memoized per call. It walks back through every ancestor:
    - `available(P)` = `inherited(P)` + P's own `$variable` (the node's own value wins).
    - `inherited(N)` = the fan-in merge of the parents' `available`.
  - Fan-in order: the index of the target port in `node.data.inputs`, then `targetHandle`, then source id. The first value per key wins. A value equal by `FlowVariables.valuesEqual` (JSON-value, numeric-aware: `5` and `5L` match) is merged silently. Never compare with `==`: after Temporal's JSON round trip the same number can have different JVM types. A different value is a `Conflict`, logged as a warning only at the node where the branches meet.
  - `nodeToOutputsMap` keeps each node's own `$variable` as the worker returned it, so the variables are never stored accumulated. `NodeReadiness` and the progress count ignore it.
  - The accumulated input is not size-capped here.
- Node status updates: `setNodeAnimationAndStatus()` marks nodes `SCHEDULED` (on dispatch), `SUCCESS`, `FAILED` or `SKIPPED` and animates/de-animates incoming edges; the worker's activity signal moves `SCHEDULED` → `BUSY`. `setEdgeStatus()` sets `edge.data.status` on every edge whose source has finished: `DELIVERED`, or `BROKEN` when it will never carry data (the workbench draws a broken wire). `NodeReadiness` uses the same commons `EdgeStatus`, with `null` meaning pending. Both mutate the in-memory workflow model used for Kafka events. Skipped nodes count as done in the progress percentage and are never in `nodeErrorsMap`.
- Final run status: after the DAG ran to its end, `ContinuumWorkflow.publishCompletion` publishes `FAILED` with search attribute `WORKFLOW_EXECUTION_FAILED` when `nodeErrorsMap` is non-empty (a failed node or loop), otherwise `FINISHED` with `WORKFLOW_EXECUTION_COMPLETED`; `start()` then raises the `WorkflowExecutionFailed` failure. The message-bridge stores that status as `workflow_runs.status`, so never publish `FINISHED` for a run that will fail. One upsert either way (Temporal matches an upsert on replay by command type only). `notifyTerminating` publishes `TERMINATED` when the run can still process a workflow task; a run that cannot (stuck retrying a task) never runs it, so the api-server writes `TERMINATED` to `workflow_runs` itself once Temporal has terminated the run. Do not rely on the handler as the only writer of that status.
- `sendUpdateEvent()` skips publishing during Temporal replay (`WorkflowUnsafe.isReplaying()`).
- `WorkflowStatusReporter.publishUpdate` is also called from signal handlers (`notifyCancelling`, `updateNodeProgressSignal`), which can arrive before `start()` has stored the workflow model: the API server sends `notifyCancelling` right after the start, while task queues are still being resolved. With no model there is nothing to report, so it returns without publishing. Never use `!!` on the model there: a throw fails the workflow TASK, Temporal retries it forever, and the run stays `RUNNING` with no status. `notifyCancelling` pins the terminal status first, so the next real update carries it.
- Temporal search attributes: `Continuum:ExecutionStatus` (Int) and `Continuum:WorkflowFileName` (Keyword) — must be created in Temporal before use (handled by `temporal-search-attributes-init` Docker service).
- Activity options: `startToCloseTimeout = 60 days`, exponential backoff with `maxAttempts = 500`, `heartbeatTimeout = 5 minutes` per node activity stub.
- Built-in node registration: `registration.BuiltinNodeRegistrationPublisher` sends one `FeatureRegistrationRequest` per entry of `registration.BuiltinNodes.all` (today the Loop: node id `LoopNode.NODE_MODEL`, feature id `org.projectcontinuum.core.builtin`, task queue `TaskQueues.BUILTIN_NO_ACTIVITY`, worker id `orchestration-<uuid>`, manifest = `LoopNodeDescriptor.nodeData` as JSON, its documentation and categories) at `ApplicationReadyEvent`, keyed by node id, on binding `continuum-core-event-FeatureRegistration-output` (Avro through the schema registry, same block as the worker starter's). The message bridge stores it like any worker registration. The event handler returns at once: each registration is a `RetryingRegistration` on one daemon thread `builtin-node-registration` (`RegistrationRetryPolicy`: 5 attempts, waits 5, 10, 20, 40 s, about two minutes; WARN per failed attempt, one ERROR naming the node and the attempt count after the last; nothing sent after a success; one worker id per start reused by every attempt); `@PreDestroy` stops pending retries. `BuiltinNodeRegistrationSender` does one send and never throws. Add a new built-in node to `BuiltinNodes`, not to the publisher.
- Config: `continuum.core.orchestration.api-server-base-url`; the schema registry `CONTINUUM_KAFKA_MAIN_SCHEMA_REGISTRY` (built-in registrations)
- Loop condition engine: comes from `continuum-loop-condition` (cel-java 0.15.0; this service and api-server are its only consumers, so they alone run protobuf-java 4.36.2 / guava 33.7.2-jre; `protobuf-java-util` is pinned to the same 4.36.2 by a constraint in `build.gradle.kts`, catalog `protobuf-java-util`). `config.LoopConditionEngineConfig` installs `CelLoopConditionEvaluator` and a `TimeBoxedConditionEvaluationRunner` into `workflow.loop.LoopConditionEvaluators` at bean start and warms the evaluator up there (first use loads cel-java, about 100 ms, which must not happen on the workflow thread); `@PreDestroy` closes the runner with `shutdownNow` and never waits for a stuck evaluation. `spike.CelInWorkflowSpikeTest` (cel-java on the test classpath via `libs.cel`) stays as the regression test: it evaluates a CEL condition inside a Temporal test workflow and replays the history with `WorkflowReplayer` (no non-determinism, no failed workflow task). Keep it green across cel-java and Temporal upgrades.
- Loops (package `workflow.loop`; `WorkflowDagExecutor` only delegates through `WorkflowLoops`, and a workflow without loops gets `WorkflowLoops.NONE` and the exact old path):
  - A loop node has no activity: `WorkflowActivityInitializer` asks task queues and builds stubs only for non-loop nodes (`LoopNode.isLoop`), and `NodeReadiness` never returns a loop as ready or skippable.
  - `NodeDispatchPayload.of(node)` is what `WorkflowDagExecutor` sends to a worker: the node without `parentNode` and `data.collapsed`, so workers on an older commons never see the loop fields (a node without them is passed through as is).
  - Execution: `WorkflowLoopsFactory.current.create(...)` builds a `LoopRunner` per run; on every pass the executor calls `advance()` (alternating with the skip pass until neither changes anything) and passes `gate()` and `carriedByLoopId()` on. `LoopRunner` per loop (state `LoopRunState`, outermost first): starts when every edge entering it delivered (any broken: loop and members SKIPPED); `LoopStartCheck` checks the settings and condition with the injected `LoopConditionValidator` (production `LoopConditionValidators.default`) and records the verdict in `Workflow.sideEffect`, so replay cannot change the start decision after a cel-java upgrade. The start verdict is cached by loop id and the compiled condition by loop id plus condition text for the run, so restarting a nested loop does not revalidate or recompile it. A rejected loop fails with "Loop 'L' cannot start: ..." instead of throwing; `check: before` checks first (false: zero iterations, members SKIPPED, loop SUCCESS "Condition was false before the first iteration"); a loop with no non-loop node inside it at any depth runs no iteration and ends WARNING "The loop has no nodes inside it to run; it ran no iteration" (no condition check); an iteration ends when nothing inside is scheduled, running or ready and nested loops have finished; a failed member fails the loop; when no node inside produced outputs or an error in the iteration (all skipped) the loop is SKIPPED "No node inside the loop could run in iteration k" (no condition check; the nodes after it are skipped), because otherwise it repeats to `maxIterations` inside one workflow task, where `historyLength` does not change and the history guard is blind; otherwise the carried variables are updated and the condition is checked: true resets (`LoopReset`: outputs, errors, status, progress of every node inside, data and animation of every inner edge, nested loop states dropped), runs `LoopHistoryGuard` and starts the next iteration, or applies `onLimit` at `maxIterations` ("Loop 'L' reached its limit of N iterations and the condition still holds." / WARNING "Stopped at the limit of N iterations"); false ends with SUCCESS "Finished after k iterations".
  - Condition check: `LoopConditionCheck` evaluates with `LoopConditionEvaluators.current` inside `Workflow.sideEffect` (`ConditionOutcomeRecorder.TEMPORAL`, outcome stored as `RecordedConditionOutcome`), so outcomes and their failure messages are replay-safe. A cel-java or time-zone data change cannot change a recorded start verdict or condition outcome. One marker event is recorded for each loop-start verdict and each condition check.
  - Bounded wait: inside that side effect the evaluation goes through `LoopConditionEvaluators.runner` (a `ConditionEvaluationRunner`; production `TimeBoxedConditionEvaluationRunner`, `DIRECT` when tests install only an evaluator). The evaluator's own budget acts only between values, so one long function call (`sets.equivalent` over two 9,000-element lists, about 1 s) would hold the workflow thread past Temporal's one-second deadlock detector; the side effect would never be recorded and every retry would evaluate again. The runner evaluates on a fixed pool of 4 named daemon threads (`loop-condition-evaluation-<n>`, queue 200, `AbortPolicy`) and waits at most `MAX_EVALUATION_MILLIS` + `WAIT_MARGIN_MILLIS` (200 + 50 ms). Started and still running after the 200 ms budget when the wait ends: LIMIT_EXCEEDED with `LoopConditionLimits.evaluationTimeExceededDetail()` (the same text as the evaluator's budget), `cancel(true)` interrupts the thread (the evaluator stops at its next value), late result discarded, one WARN with loop, check point and workflow/run id, never a value. No thread in time (queue full, still queued when the wait ends, or started less than the budget before it): the threads are shared by every run, so this is not the condition's outcome. `ConditionEvaluationUnavailable` is thrown, whichever run holds the threads (nothing recorded, one WARN "... nothing is recorded and the workflow task is retried", Temporal retries the task): slow conditions delay a loop's check, never fail it. A queued check is withdrawn (`EvaluationTicket`: start and withdraw race through one atomic state, so a withdrawn check never runs) and at most 4 abandoned evaluations exist. Runner stopped or the waiting thread interrupted: `ConditionEvaluationUnavailable` too. Never catch `ConditionEvaluationUnavailable` inside the side effect, or it is recorded as the loop's outcome. Retry pacing: the SDK reports only a task's first failed attempt (one `WORKFLOW_TASK_FAILED`) and lets later attempts time out (`ReplayWorkflowTaskHandler`), so a retried check runs once more at once and then at growing intervals of at least the workflow-task timeout (10 s by default; measured on a real server: 10, 10, 15, 18, 27, 47, 90, 143, 270 s), and cannot flood the history (later attempts are transient: about 3 events per wait). Each attempt after the first also logs an ERROR stack trace from the SDK poller ("Failure processing workflow task ... ConditionEvaluationUnavailable"): expected, not a fault; an abandoned call frees its thread when its one cel-java call returns (about 1 s for `sets.equivalent` over two 9,000-element lists; the caps allow up to about 9 s for one call built from literals). Known limit, not fixed (self-starvation): a run with more parallel loops with very slow conditions than there are evaluation threads (4), whose checks fall into one task, holds all threads with its own abandoned calls; its remaining check is retried, and every retry evaluates the task's checks again and abandons them again, so the run keeps retrying and stays `RUNNING` until a retry finds enough free threads (measured: 5 parallel loops each with one stuck call, still `RUNNING` after 12 min, never ending on its own); until it is terminated, every retry holds all 4 threads again for up to about 9 s and delays every other run's loop checks, across tenants. Terminating it sets the run record to `TERMINATED` (the api-server writes it; the run cannot). Known limit, not fixed: there is no total per workflow task. Each slow check costs the task up to about 250 ms, so many parallel loops with slow conditions whose checks fall into one task add up (measured: 24 loops, 6.3 s; 30 loops, 7.9 s); at about 40 the task passes Temporal's 10 s workflow-task timeout, nothing is recorded, every retry evaluates them all again, and the run stays `RUNNING` (48 loops with a slow macro condition: still `RUNNING` after 45 s, 4 task timeouts, 0 markers). The bounded `Future.get` is the only thing workflow code blocks on, and only while recording, so replay never waits: never call the runner outside the recorded side effect. `ConditionOutcomePolicy` maps the outcome to a `LoopDecision`; `onNonBooleanResult` is one `NonBooleanResultStrategy` object per value: `fail` → FAILED "Loop 'L': the condition returned a string ("yes") in iteration 2, not true or false."; `treat-as-false` → WARNING "Condition returned string in iteration 2; treated as false." (members SKIPPED on a `before` first check). A failed check fails the loop: MISSING_VARIABLE "Loop 'L': flow variable 'hasMore' is not set when the condition is checked in iteration 3 (column 1).", other codes "Loop 'L': the condition check in iteration k failed with CODE: the condition <message>.".
  - `LoopHistoryGuard`: before every iteration, more than 40,000 events (`LoopBudget.MAX_HISTORY_EVENTS`) or 40 MiB fails the loop whatever `onLimit` says ("Loop 'L' stopped before iteration k: the run history has N events and would reach Temporal's limit. ..."). Thresholds are code constants with a constructor override (tests install a factory with a small guard).
  - `LoopStatusPublisher`: loop `data.status` BUSY while iterating, then SUCCESS / WARNING / FAILED / SKIPPED; `nodeProgress` `Iteration k of max` (percentage k*100/max), then the final message; on finish the display-only `nodeToOutputsMap[L]["$variable"]` (what the last iteration's entry members received, omitted when empty); on failure `$error` (text/plain) in `nodeErrorsMap`, which fails the run, and the untouched nodes inside are SKIPPED; `skipped` for a loop skipped after it started (status SKIPPED, the reason as progress text, no `$error`). Edges leaving a failed or skipped loop are BROKEN, so the nodes after it are skipped.
  - Progress (`WorkflowProgress`, `MonotonicProgress`): the share of done non-loop nodes; `WorkflowStatusReporter.publishUpdate` publishes the highest value so far, so resetting loop members between iterations never moves it backwards. The maximum is updated on replay too, so it is deterministic.
  - Loop-carried flow variables: `FlowVariableMerger.collectInputVariables(..., loopTopology, carriedByLoopId)` overrides an entry member's fan-in result with the carried variables of every loop it is an entry member of, outermost first; `LoopRunner.carriedByLoopId()` holds the set of every iterating loop and of every loop that finished SUCCESS or WARNING after at least one iteration (`LoopRunState.passesCarriedVariablesOn`), so a node after the loop, which inherits through the entry member, gets the last iteration's set and the display `$variable` matches what was passed; a loop with zero iterations, FAILED or SKIPPED passes nothing on, and a nested loop's state (and so its set) is dropped when its enclosing loop restarts; `LoopCarriedVariables.afterIteration` builds the next carried set (previous set, then each member's own variables in `LoopTopology.topologicalOrder`, later member wins); `FlowVariableMerger.endOfIterationVariables` is what a loop condition reads (outside parents' variables, then the carried set). Several outside parents setting one name: the entering edges are ordered by the target member's run order in the loop, then the target's input port index, `targetHandle`, source id; the first value wins. Defaults keep loop-free merges unchanged. The workbench's `FlowVariables.ts` mirrors the rule; `src/test/resources/flow-variables/loop-carry-cases.json` is the shared case list (SHA-256 pinned in `FlowVariableLoopCarryCasesTest`): change the Kotlin rule, the TypeScript rule and the file together.
  - `LoopTopology.of(workflow)` — built once per run from `parentNode`: `loopIds`, `innermostLoopOf`, `directMembers`, `descendants`, `enclosingLoops` (outermost first), `entryMembers` (non-loop descendants with no incoming edge from inside), `externalIncomingEdges`, `outwardEdges`, `edgesInside`, `topologicalOrder` (Kahn, ties by `nodes` order; the variable clash rule uses it). Malformed parents (unknown, not a loop, cycle) are ignored, never followed forever.
  - `LoopReadinessGate(topology, activeLoopIds, finishedLoopIds, failedOrSkippedLoopIds)` — passed to every `NodeReadiness` function (default `LoopReadinessGate.NONE` = the old behaviour). An edge leaving a loop is pending until the loop finished, `BROKEN` when it failed or was skipped, then judged by its source; a node inside a loop is ready or skippable only while every enclosing loop is active.
  - The engine seam `LoopConditionEvaluator` is defined engine-free in commons `validation.loop`; `workflow.loop.LoopConditionEvaluators.current` is the process-wide instance (Temporal creates the workflow class, so it is reached statically; `install`/`reset`, and `current` fails clearly when nothing is installed).
  - Tests: `fixtures.ScriptedLoopConditionEvaluator` (scripted outcomes per call or a function of the variables, records what it saw; no engine), `fixtures.LoopRunHarness` (Temporal test environment, captured status events copied at send time, replay), `fixtures.LoopWorkflowBuilder` / `LoopFixtures` (loop models). `ContinuumWorkflowLoopTest` (scripted), `ContinuumWorkflowLoopReplayTest` (real evaluator, `WorkflowReplayer`, replay with a different evaluator installed; one long `sets.equivalent` over two list variables with the production runner and a 500 ms deadlock detector: loop FAILED, 0 workflow-task failures, replays), `LoopConditionCheckTest` and `TimeBoxedConditionEvaluationRunnerTest` (wait bound, interrupt, held pool and late start retried instead of recorded, shutdown), `ContinuumWorkflowLoopEvaluationPoolTest` (Temporal level, production runner: a loop whose check finds every thread held by other runs' stuck evaluations finishes SUCCESS after a task retry with one marker; a check on stopped threads leaves no marker and the retried task finishes the loop; all replay) (`LoopRunHarness` takes a `runner`, a `deadlockDetectionTimeoutMillis` and a `workflowTaskTimeout`; the test server can number a fresh task as attempt 2, which the SDK then leaves to time out, so retry tests use 2 s), `ContinuumWorkflowLoopHistoryBudgetTest` (events per member run and per check within 20 % of `LoopBudget`).

## Work Guidance

- README: every change here updates the repository root `README.md` (module table, How It Works) in the same change (root `AGENTS.md`, "User Preferences").
- Temporal workflow code must be deterministic — no `Date.now()`, `Math.random()`, or I/O. Use `Workflow.getLogger()`, not a static logger. Side effects go in activities.
- `nodeIdToActivityMap` holds per-node activity stubs, each routed to the correct task queue. Do not share a single stub across different queues.
- `nodeErrorsMap` uses the `$error` output port as the sentinel. Any output map containing `"$error"` key means the node failed.
- Workflow is cancelled via `CanceledFailure` (Temporal cancellation or termination). All SCHEDULED and BUSY nodes are marked CANCELLED, and the event is published.
- `FakeContinuumNodeActivity` returns `flowVariablesToSet` under `$variable`, like the worker. With `emitDefaultFlowVariables = true` it also adds the worker's `DefaultFlowVariables` (built with the same commons code, `outputRowCounts` per port), on success and on `$error`. It is off by default so the merge-rule tests can assert exact maps. Turn it on in any test about what real workflows carry. Keep it in step with `ContinuumNodeActivity.withDefaultFlowVariables`.
- Test fixtures in `src/test/resources/test-workflows/` that name a real node model (e.g. `SplitNodeModel`) must carry properties valid against that node's registered schema, not just the copy in the file. `WorkflowPropertiesValidationTest` checks this and covers the invalid-property cases: one attempt, no retry, downstream nodes do not run. To enable that check in other tests, set `FakeContinuumNodeActivity.registeredSchemas`.
